# Key Points

This is the short breakdown of the practices that matter most.

## 1. Trunk-based development is about one shared line of development

The central idea is that developers collaborate on a single branch, usually `main`, and avoid long-lived development branches. The point is to reduce merge pain, keep integration continuous, and maintain a releasable codebase.

## 2. Short-lived branches are allowed, long-lived branches are not

Pull-request workflows are fine if branches are short-lived, usually no more than a couple of days, and owned by one developer or one pair. Once work lasts for weeks, the team is back in the failure mode trunk-based development is designed to eliminate.

## 3. Continuous integration is not optional

If multiple developers are contributing, automated validation is required. Developers should run the same build logic locally that CI runs centrally, and CI should validate both incoming changes and the shared trunk after merge.

MinimumCD makes the same point more bluntly: if developers are not integrating to trunk daily, the team is not yet doing real CI and cannot claim continuous delivery readiness.

## 4. Incomplete work belongs behind toggles, not in branches

When work cannot be completed in one small slice, the guidance is to keep integrating incrementally and hide incomplete behavior with feature flags or similar runtime controls. For Salesforce, that often means custom metadata, custom permissions, permission sets, or configuration-driven routing.

## 5. Larger changes need structure, not isolation

For changes that take longer, use branch by abstraction: introduce an abstraction, build the new implementation behind it, switch traffic, then remove the old path. This maps well to Apex service layers, integration adapters, and domain logic refactors.

## 6. Releases should not slow normal development

Teams should not freeze the trunk just because a release is approaching. If release branches are needed, they are cut late and used narrowly. High-cadence teams can release directly from trunk and fix forward.

## 7. The anti-pattern is familiar

The site is explicit about what does not count as trunk-based development:

- Branches lasting beyond a couple of days.
- Multiple developers sharing the same feature branch for general development.
- Partially complete work merged around between branches.
- Release periods causing code freezes, slowed integration, or branch gymnastics.

## 8. Salesforce implication

The key inference for Salesforce is simple: stop treating long-lived sandboxes and long-lived branches as the place where integration happens. Integration should happen continuously in source control and CI, with orgs used for validation and testing, not as parallel lines of truth.

## 9. There are two acceptable migration paths

MinimumCD describes two ways to adopt TBD:

- Short-lived pull-request branches that merge within a day.
- Direct trunk commits backed by strong tests and fast feedback.

For most Salesforce teams, the first path is the realistic starting point because compliance expectations, slower validation, and metadata complexity usually make an immediate jump to direct commits too abrupt.

## 10. Measure branch age and integration health

The migration guide recommends baselining branch lifetime, merge-conflict frequency, delivery speed, and quality indicators before changing policy. That advice is useful for Salesforce teams because it turns the rollout into an observable operational change rather than a debate about preferences.
