# Trunk-Based Development for Salesforce

This documentation turns the guidance from [TrunkBasedDevelopment.com](https://trunkbaseddevelopment.com/) into a practical operating model for Salesforce teams.

It also incorporates migration guidance from the MinimumCD Practice Guide:

- [Trunk-Based Development](https://beyond.minimumcd.org/docs/migrate-to-cd/foundations/trunk-based-development/)
- [TBD Migration Guide](https://beyond.minimumcd.org/docs/migrate-to-cd/foundations/trunk-based-development/tbd-migration/)

## What this site covers

- The core ideas behind trunk-based development.
- The key practices that matter most for delivery teams.
- The migration choices, metrics, and team agreements that help teams move from long-lived branches to daily integration.
- How to adapt those practices to Salesforce DX, scratch orgs, pull requests, validation, and release management.
- A starting sequence for teams moving away from long-lived branches and sandbox-heavy workflows.

## Core position

The source material defines trunk-based development as a model where developers collaborate on a single shared branch and avoid long-lived development branches through disciplined techniques. It also ties trunk-based development closely to continuous integration and, by extension, continuous delivery.

For Salesforce teams, that usually means:

- `main` stays the integration branch.
- Feature branches, if used, are short-lived and owned by one developer or one pair.
- Daily integration is the non-negotiable threshold. If work is not reaching trunk at least once per day, the team is not yet operating in the model these sources describe.
- Every change is validated automatically before and after it reaches `main`.
- Incomplete work is hidden with toggles, permissions, or abstraction instead of being isolated for weeks in a branch.
